Architecture overview
Unified sales analytics on MongoDB
The question

Four paths to one collection

Online, in-store, and partner sales each live in their own collection. Your users want a single, pre-aggregated view they can query. The aggregation itself is the easy part — what really decides the design is when it runs and where the result lands.

The shape stays the same in all four approaches. What changes: the engine in the middle, and the box on the right.

Before choosing

Two questions decide almost everything

You could skip materializing altogether and read across the three collections at query time with $unionWith. That works, and it is a perfectly good place to start when volumes are small — but every user pays the full aggregation cost on every query, and that cost grows with your history, not with your traffic. Materializing the result once and serving it many times is what breaks that link.

Once you decide to materialize, the aggregation pipeline is broadly the same whichever path you take. The four approaches below differ on two axes only:

Scheduled batch refresh

The classic on-demand materialized view. One pipeline reads all three collections, aggregates, and upserts the result. It runs on a clock — hourly, nightly, whatever the business can live with.

Freshness
Minutes to a day
Users query
Atlas collection
Moving parts
None new
Cost shape
Bursty, on your cluster

How it works

  1. A scheduler fires — an Atlas Scheduled Trigger, Airflow, or a cron job on your side.
  2. The pipeline reads only what changed since the last run, using a watermark such as updatedAt.
  3. $unionWith folds the other two collections in, and a shared $project normalizes their differing shapes into common fields.
  4. $group computes the rollup, and $merge upserts each result document into the analytics collection by key.
Nothing moves between ticks. All the work — and all the load — lands in one burst. 
// Atlas Scheduled Trigger, hourly
db.sales_online.aggregate([
  { $match:     { updatedAt: { $gte: lastRun } } },
  { $unionWith: { coll: "sales_instore",  pipeline: [ /* normalize */ ] } },
  { $unionWith: { coll: "sales_partners", pipeline: [ /* normalize */ ] } },
  { $group:     { _id: { day: "$day", region: "$region", channel: "$channel" },
                  revenue: { $sum: "$amount" }, orders: { $sum: 1 } } },
  { $merge:     { into: "sales_rollup", on: "_id", whenMatched: "merge" } }
])

Simplified for illustration — real pipelines carry more normalization and date handling.

Works well when

  • No new infrastructure. It runs on the cluster you already operate and pay for.
  • The whole transformation is in one readable place — easy to review, version, and hand to a new engineer.
  • Re-running is trivial. Backfills, corrections, and schema changes are just another run over a wider window.
  • Prefer $merge over $out: it updates incrementally instead of replacing the collection, so readers never see an empty view and you can watch the result with a change stream.

Watch out for

  • The numbers are wrong between runs — by design. Everyone querying at 3pm sees the 2am picture.
  • The burst competes with production traffic. Point the read at an analytics node so the scan does not sit on top of your write path.
  • Watermark logic is subtler than it looks. Late-arriving partner files and back-dated corrections slip past a naive updatedAt filter.
  • Deletes need a plan. A pipeline that only reads current documents will never remove a rollup for data that was deleted.

Per-document triggers

A trigger on each source collection fires a function for every insert, update, and delete, and that function updates the matching rollup document. Reactive, granular — and the approach that looks easiest at the start and ages hardest.

Freshness
Seconds
Users query
Atlas collection
Moving parts
3 functions
Cost shape
Per invocation

How it works

  1. A Database Trigger is configured on each of the three collections, each watching its change stream.
  2. Every document change invokes a function, receiving that one change event.
  3. The function maps the document to a rollup key and applies an atomic update to the analytics collection.
Three independent writers, no shared clock. Nothing coordinates their order or groups them into a window. 
// Database Trigger function — fires once per changed document
exports = async function (changeEvent) {
  const doc = changeEvent.fullDocument;

  // no window, no batch: the update itself must be atomic
  await rollup.updateOne(
    { _id: { day: doc.day, region: doc.region, channel: doc.channel } },
    { $inc: { revenue: doc.amount, orders: 1 } },
    { upsert: true }
  );
};

Read–modify–write here instead of $inc would lose increments under concurrency.

Works well when

  • You are copying documents, not aggregating them — projecting each sale into a unified feed is exactly what this is good at.
  • Volumes are modest and the appeal of no extra infrastructure outweighs the ceilings below.
  • You need a side effect, not just a number — notify, enrich, call an external service on each sale.

Watch out for

  • Aggregation gets hard fast. Each invocation sees one document with no window, so every rollup becomes an atomic counter update — workable for sums and counts, awkward for distinct counts, averages, or top-N.
  • Updates and deletes need the previous value to adjust a running total. That means enabling pre-images and handling every operation type, not just inserts.
  • No ordering guarantee across the three collections, and no natural way to reprocess a window that went wrong.
  • Cost and throughput scale with write volume, not with how much analysis you actually need.
  • Backfilling history is a separate job. Triggers only see changes from the moment you switch them on — so you end up writing the batch pipeline anyway.

Stream processing into a collection

One managed processor reads the three change streams continuously, unions and normalizes them, aggregates inside time windows, and merges each window's result into the analytics collection. A materialized view that maintains itself.

Freshness
Seconds
Users query
Atlas collection
Moving parts
1 managed processor
Cost shape
Continuous, sized tier

How it works

  1. $source opens a database-level change stream and a $match narrows it to the three sales collections — one stream, not three.
  2. Ordinary aggregation stages normalize the differing shapes into common fields, in flight.
  3. $tumblingWindow collects events into fixed intervals and runs the $group inside each one — so aggregation happens over a defined set of events, not one document at a time.
  4. When a window closes, $merge upserts its results into the analytics collection.
Continuous in, periodic out. The window is what makes the aggregation correct — and what sets the freshness. 
[
  { $source: { connectionName: "salesCluster", db: "sales",
              config: { fullDocumentOnly: true } } },

  { $match: { "ns.coll": { $in: ["online", "instore", "partners"] } } },

  { $tumblingWindow: {
      interval: { size: 1, unit: "minute" },
      pipeline: [
        { $group: { _id: { day: "$day", region: "$region", channel: "$channel" },
                    revenue: { $sum: "$amount" }, orders: { $sum: 1 } } }
      ] } },

  { $merge: { into: { connectionName: "salesCluster",
                     db: "analytics", coll: "sales_rollup" } } }
]

The $group is the same one from the batch pipeline — only the runtime around it changed.

Works well when

  • You want fresh numbers without rewriting how you query. The result is still a normal collection, so the app, Atlas Charts, and BI tools need no changes at all.
  • Windowing makes aggregation correct by construction — no hand-rolled atomic counters, no lost updates, and averages and distinct counts are just ordinary stages.
  • It is the same aggregation language your team already writes. The step up from the batch pipeline is small.
  • Analytics compute moves off the operational cluster, so a heavy rollup no longer competes with checkout traffic.
  • Reliability is built in: checkpointing, and a dead-letter queue for documents that fail to process instead of a silently dropped sale.
  • Backfill is supported — $source can be configured to read existing documents before switching to live changes.

Watch out for

  • It is a component you size and monitor, with a cost that runs continuously — including overnight when nothing is selling.
  • Late and out-of-order events need a decision. How long a closed window stays open for stragglers is a business question, not a default.
  • Window size is the freshness dial. Shorter windows mean fresher numbers and more write traffic to the target collection.
  • Restating history — a repricing, a corrected partner feed — is still cleanest as a one-off batch run over the affected range.

Stream processing into the lakehouse

The same processor, a different destination. Instead of a collection, the output becomes Apache Iceberg tables on S3 — read by Snowflake, Databricks, Athena, or Trino. This is the one that changes where your users actually run their queries.

Freshness
Seconds to minutes
Users query
Warehouse / lakehouse
Moving parts
Processor + catalog
Cost shape
Cheap storage, engine compute

How it works

  1. The front of the pipeline is identical: source the change streams, normalize, optionally aggregate.
  2. $iceberg replaces $merge as the final stage, writing Iceberg v2 tables into an S3 bucket. In cdc mode it applies inserts, updates, and deletes as row-level changes rather than appending duplicates.
  3. The table is registered in a catalog — AWS Glue or Hadoop — so query engines discover it automatically, and schema changes are handled as the tables evolve.
  4. Analysts query it from whichever engine they already use. MongoDB is no longer in the read path.
MongoDB writes the tables; the engines pull from them. The read path no longer touches your cluster at all. 
  // ...same $source and normalization as above...

  { $iceberg: {
      connectionName: "salesLake",
      bucket:         "acme-analytics",
      path:           "iceberg-warehouse/",
      databaseName:   "sales",
      tableName:      "sales_rollup",
      mode:           "cdc",
      idFieldName:    "_id",
      catalog:        { type: "glue" }
  } }

Sink stages are mutually exclusive — a processor writes to a collection or to the lake, not both.

Works well when

  • Sales analysis has to sit next to other enterprise data — finance, inventory, marketing spend — and the joins belong in a warehouse, not in MongoDB.
  • You need years of history cheaply. Object storage costs a fraction of keeping the same data on cluster disk.
  • Analysts already live in Snowflake or Databricks and want the sales data to show up there, in their own tools.
  • Open format, no lock-in. Iceberg is readable by every major engine, and the catalog keeps the schema honest as it evolves.
  • Full-table scans stay off the operational cluster entirely — the heaviest queries never touch the database serving your customers.

Watch out for

  • It changes who can consume the result. An application that needs a single rollup by key in a few milliseconds still needs something in Atlas — the lake is not a serving layer.
  • You are now operating a lakehouse: the bucket, the catalog, permissions, and a query engine with its own bill.
  • Visibility follows the commit cadence, not the event — data appears when files are committed to the table, so tune write intervals rather than expecting instant reads.
  • Small-file pressure is real. Very frequent commits create many small files, and Iceberg tables need periodic compaction to stay fast.

Choosing

A decision path, in the order the questions matter

There is no single right answer here — but there is a right order to ask the questions in. Freshness first, because it eliminates the most options. Consumption second, because it determines the sink.

First ask

Are you aggregating, or just copying documents?

Just projecting each sale into a unified feed, one document in, one document out. Triggers are a fine fit
Computing sums, counts, averages, or rankings across many documents. Keep going ↓
Then ask

How fresh must the numbers be?

A daily or hourly refresh matches how the business actually reads the report. Scheduled batch
Store managers and partners expect to see today's sales within seconds. Keep going ↓
Finally

Where will the result be consumed?

From the application, Atlas Charts, or a BI connector — inside Atlas, low latency, by key. Stream → collection
In the warehouse, joined to other enterprise data, over years of history. Stream → Iceberg on S3
Honestly, both — an operational view and a deep analytical one. Run both sinks
In practice

Most production setups use two of these

These are not four competing products to pick between — they are four runtimes for broadly the same pipeline, and they compose well. The common pairings:

STREAM + BATCH

Live view, nightly truth

Stream processing keeps today's numbers current; a nightly batch recomputes the closed days from source. Late partner files and corrections get absorbed without anyone hand-patching a rollup.

STREAM + LAKE

Serving layer and history

One processor merges a rolling window into Atlas for the app to read by key; a second writes the full event history to Iceberg for the analysts. Same source, two audiences.
